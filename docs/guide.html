Agent Harness Eval 図解ガイド

Claude Code / Codex の配布物（CLAUDE.md・スキルなど）を、同じタスクで隔離して実行・採点し、配布物なしや前回版と比べる仕組みを図で説明します。詳しい設定項目は README.md、設計の理由（既存ツールとの比較・評価の方法・採らなかった案）は 設計記録 を参照してください。

1. 全体像2. 使う順番3. 実際の依頼からタスクを作る4. 1 試行の流れ5. 隔離6. 採点7. 指標8. トークン節約9. 出力

1. 全体像

用意するのは 4 種類のファイルだけです。harness-eval がそれを「タスク × プロファイル × 試行回数」に展開し、1 試行ずつ隔離して実行・採点・集計します。

用語意味同梱サンプルの例
タスクエージェントにさせる仕事 1 つ（プロンプト・入力データ・採点方法）csv-summary-format「sales.csv を月別に集計して」
プロファイルどのエージェントを、どの配布物で動かすかclaude-baseline（配布物なし）・claude-ds-lite
配布物（ハーネス）評価したい設定一式。プロファイルの install で一時ホームに展開examples/harnesses/ds-lite/
試行1 タスク × 1 プロファイルを 1 回実行して採点したものcsv-summary-format / claude-ds-lite #0
グレーダー採点ルール 1 つ。結果（ファイル・応答）か過程（ツール・スキル・サブエージェント・hook の呼び出し）を見る「summary.md に表ヘッダがある」
ベースライン比較の基準にするプロファイル（通常は配布物なし）--baseline claude-baseline

2. 使う順番

評価に使うタスクは、まず harvest で自分のセッション履歴から用意します（§3。履歴がなければ同梱の標準タスク）。その後は費用がかからない確認を先に済ませ、エージェントを呼ぶのは必要な分だけにします。普段回すのはスモークだけです。

3. 実際の依頼からタスクを作る（harvest）

評価は、ユーザーが実際に頼む仕事で行うのがいちばん確かです。harvest は自分のセッション履歴から実際の依頼を集め、同じ種類・同じ難しさのまま、名前・数値・データをすべて架空に置き換えたタスクの下書きを作ります。元の依頼をそのまま実行したり、本物のデータや環境に触れたりはしません。

心配対策
社外秘が残る固有名詞・数値・日付・表名を架空化。元の識別子・URL・メール・大文字の名前・年月・4 桁以上の数値・25 文字以上の同じ文が残った案は自動で作り直し／見送り。日本語の会社名・人名は機械では判定できないため、人の確認が必須
依頼文がファイルやログに残るメモリ上だけで扱い、表示は件数だけ。書き換えの呼び出しも新しい履歴を作らず、テレメトリのプロンプト記録も外す
LLM が書いた採点スクリプトharvest では実行しない（構文の確認だけ）。人が読んだあとに validate --selftest で、正解例で通り何もしなければ落ちるかを確かめる
本物の環境で実行してしまう合成データだけで完結する形に書き換える。Claude Code では ssh・curl・Hive・Trino などを禁止（Bash(ssh *) の禁止が効くことを実機で確認。Bash 自体は使えるので最善の努力）。Codex はサンドボックス（既定でネットワーク不可）で制限。.claude/・CLAUDE.md などの設定ファイルは置かせない
採点が不公平正解例で通り、何もしなければ落ちることを自動確認。依頼で求めていない判定は外す

開発時に合成の依頼 3 件で試すと、3 件とも元の名前・識別子が残らない下書きになり、配布物なしの haiku で 3/3 解けました。ただし改善 SQL の書き方を 1 通りに決め打ちする採点スクリプトも出たので、使う前に「正しいが書き方の違う答えを落とさないか」を確認してください。

4. 1 試行の流れ

1 試行は 4 つの部品の間を順に進みます。エージェントに渡るのは「配布物だけを置いた一時ホーム」と「フィクスチャを複製した作業ディレクトリ」です。

5. 隔離：エージェントから何が見えるか

普段の設定（ホームの .claude・.codex）は読み込ませず、試行ディレクトリに置いた配布物で起動します。ただし CLI は作業ディレクトリより上のフォルダの CLAUDE.md・.claude/skills・AGENTS.md も読むため、--out とその上にこれらがあると run は止まり、doctor は NG にします（--out はリポジトリやホームの外に置く）。外のもので使うのは AWS の認証ファイル（参照のみ）と、指定したときの認証ファイルの複製です。これは「どの設定を読み込むか」の隔離で、ファイルの読み書きを禁止するものではありません（Read や Bash を許可すれば絶対パスで外も読めます）。そのため評価には合成データだけを使います。

環境変数試行中の値理由
HOME・USERPROFILEhome/普段のユーザー設定・スキルを読ませない（isolate_home: false で無効）
CLAUDE_CONFIG_DIR / CODEX_HOMEhome/.claude / home/.codex配布物だけを置いた設定ディレクトリで起動する
AWS_SHARED_CREDENTIALS_FILE・AWS_CONFIG_FILE本物の ~/.aws/…ホームを差し替えても Bedrock の認証を使える（未設定でファイルがあるときだけ）
CLAUDECODE など親セッションの変数削除Claude Code の中から実行しても入れ子扱いにならない
プロファイルの env追加・上書きBedrock の設定など
経路を変える変数（API キー・Bedrock の切り替え・モデルの別名など）親の値をそのまま渡すenv か inherit_env（名前だけ）で宣言する。宣言のない引き継ぎは doctor が NG

完全には隔離できないもの（Claude Code の同梱スキル、組織の管理設定など）があるため、各試行で実際に読み込まれたスキル・プラグイン・MCP を記録し、レポートの「実行環境の記録」で確認できます。

6. 採点：試行が合格・不合格・除外のどれになるか

環境のせいで落ちた試行は「失敗」に数えません。LLM 判定はコード判定が全部通ったときだけ呼ぶので、結果を変えずに判定の費用を省けます。

試行の状態例pass@1・pass^k の分母キャッシュ
合格全グレーダー合格入る保存
不合格形式違反・timeout・max_turns・budget_exceeded・agent_error入る保存（timeout は保存しない）
除外rate_limit・overloaded・auth・network・launch_failed・harness_error・judge_error・not_graded・interrupted入らない（件数と理由を表示）保存しない
未実行--max-cost-usd・--monthly-budget-usd（Claude・Codex の口座ごと）に到達（budget_stop）入らない（件数を表示）保存しない

7. 指標：pass@1 と pass^k の違い

pass@1 は「平均的にどれくらいできるか」、pass^k は「k 回続けて使っても毎回できるか」です。配布ツールは同じ人が何度も使うので、pass^k を主指標にします。

タスク3 試行の結果pass@1pass^3pass^2 ＝ C(c,2) ÷ C(3,2)
A✓ ✓ ✓（c = 3）100%13 ÷ 3 ＝ 1
B✓ ✗ ✓（c = 2）67%01 ÷ 3 ＝ 0.33
C✗ ✗ ✓（c = 1）33%00 ÷ 3 ＝ 0
全体（タスク平均）67%0.330.44

有効試行 n 回中 c 回合格のとき pass^k ＝ C(c,k) ÷ C(n,k)。n ＝ k なら「全部合格で 1、それ以外 0」です。有効試行が k 回未満のタスクは計算せず、レポートに「計算できたタスク数」を出します。Δ は比較プロファイルから基準プロファイルを引いた値で、両方に値があるタスクだけで計算します。配布物なしの基準と比べるときは、配布物がないと通らない判定（スキル・サブエージェント・hook を使うことの要求）を両側とも除きます。差にはタスク単位のブートストラップによる 95% 区間を付けます（試行を独立な標本として数えない。区間が 0 をまたげば差があるとは言えない）。

リリース判定（gate）は、前回と今回の同じプロファイルの差の区間を、結果を見る前に決めた非劣性マージン m（--margin、毎回指定）で判定します。

判定条件終了コード
通過区間の下端 ≥ −m（悪化していても m 以内と言える）0
不通過区間の上端 < −m（はっきり悪化）、安全違反（unsafe_access など）が 1 件でもある、または比較できない（k・LLM 判定の有無・タスク定義が違う、今回の結果にプロファイル・タスクがない、指標を算出できない）1
判定不能それ以外、または比較できたタスクが --min-tasks（既定 10）未満。タスクが少ないと区間は実際より狭く出やすいため3

8. トークン節約：変えたところだけ実行する

試行の入力をすべてハッシュにしてキャッシュのキーにします。配布物を変えたプロファイルだけキーが変わるので、そのプロファイルだけが再実行されます。

トークンを使う場所節約の仕組み評価の正しさへの影響
エージェントの試行キャッシュ（入力が同じなら再利用）なし
エージェントの試行スモーク（1 試行）とフル（3 試行）の使い分けスモークは傾向の確認用と割り切る。判断はフルで
エージェントの試行試行ごと（max_turns・max_budget_usd・timeout_s）・実行全体（--max-cost-usd）・月（--monthly-budget-usd）の上限上限到達は「不合格」または「未実行」として明示
LLM 判定コード判定が全合格のときだけ呼ぶ（配布物がないと通らない判定の不合格は除く）なし（不合格の試行は判定しても合否が変わらない）
LLM 判定haiku・ツールなし・1 ターン・対象は最大 2 万文字（Claude Code で判定する場合）calibrate で人手ラベルとの一致率を確認
再試行レート制限・過負荷で落ちた試行だけなし（不合格を引き直さない）
（入れていない）早期打ち切り（失敗が出たらそのタスクの残り試行をやめる）理由は 設計記録「採らなかった案」

trials.jsonl・キャッシュ・レポートには最終応答とツール呼び出しの入力が残ります。評価には合成データだけを使い、結果とキャッシュを社外に出さないでください。Ctrl-C で中断すると未開始の試行は取り消され、実行中のエージェントも止まります。完了済みの試行はキャッシュにあるので、同じコマンドを再実行すると続きから進みます。
