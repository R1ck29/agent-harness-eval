Agent Harness Eval 図解ガイド

Claude Code / Codex の配布物（CLAUDE.md・スキルなど）を同じタスクで隔離して実行・採点し、配布物なしの基準や前回の版と比べます。このページではその仕組みを図で説明します。YAML の書き方・コマンドのオプションは リファレンス、なぜこの作りなのかは 設計記録 にあります。

1. 全体像

用意するのは 4 種類のファイルです。harness-eval はそれを「タスク × プロファイル × 試行回数」に展開し、1 試行ずつ隔離して実行・採点・集計します。

用語意味同梱サンプルの例
タスクエージェントにさせる仕事 1 つ（プロンプト・入力データ・採点方法）csv-summary-format「sales.csv を月別に集計して」
プロファイルどのエージェントを、どの配布物で動かすかclaude-baseline（配布物なし）・claude-ds-lite
配布物（ハーネス）評価したい設定一式。プロファイルの install で一時ホームに展開するexamples/harnesses/ds-lite/

グレーダー採点ルール 1 つ。結果（ファイル・応答）か過程（ツール・スキル・サブエージェント・hook の呼び出し）を見る「summary.md に表ヘッダがある」

split自己改善ループでのタスクの使い道（train・dev・holdout。11 章）split: holdout

2. 使う順番

費用のかからない確認を先に済ませ、エージェントを呼ぶのは必要な分だけにします。普段回すのはスモーク評価だけです。

3. run の流れ

run は試行の一覧を作って並べ、1 試行ずつ「キャッシュ → 費用の上限 → 実行 → 再試行」の順に処理してから集計します。

4. 1 試行の流れ

1 試行は 4 つの部品の間を順に進みます。エージェントに渡すのは「配布物だけを置いた一時ホーム」と「フィクスチャを複製した作業ディレクトリ」です。

5. 隔離：エージェントから何が見えるか

普段の設定（ホームの .claude・.codex）は読み込ませず、試行ディレクトリに置いた配布物だけで起動します。外のファイルで使うのは AWS の認証ファイル（参照のみ）と、指定したときに複製する認証ファイルだけです。

環境変数試行中の値理由
HOME・USERPROFILEhome/普段のユーザー設定・スキルを読ませない（isolate_home: false で無効）
CLAUDE_CONFIG_DIR / CODEX_HOMEhome/.claude / home/.codex配布物だけを置いた設定ディレクトリで起動する
AWS_SHARED_CREDENTIALS_FILE・AWS_CONFIG_FILE本物の ~/.aws/…ホームを差し替えても Bedrock の認証を使える（isolate_home: true で、未設定かつファイルがあるときだけ）
CLAUDECODE など親セッションの変数削除Claude Code の中から実行しても入れ子扱いにならない
プロファイルの env追加・上書きBedrock の設定など
経路を変える変数（API キー・Bedrock の切り替え・モデルの別名など）親の値をそのまま渡す経路と請求先が変わるので、プロファイルで宣言させる（リファレンス「認証」）

Claude Code にはさらに --settings {"syncClaudeAiSkills":false,"syncClaudeAiPlugins":false} を渡し、claude.ai アカウントから同期されるスキル・プラグインが混ざるのを防ぎます。

隔離できないもの

  • 上のフォルダの指示：CLI は作業ディレクトリより上のフォルダにある指示・スキル・ルール・サブエージェント・コマンドも読み込みます（一時ホームでは防げません）。配布物なしの基準にも混ざって比較が壊れるため、--out とその上に CLAUDE.md・CLAUDE.local.md・AGENTS.md・AGENTS.override.md・.mcp.json や .claude/・.codex/・.agents/ フォルダがあると、run は止まり、doctor は NG にします。--out はリポジトリやホームの外（例: macOS /Users/Shared/harness-eval、Windows C:\harness-eval）に置いてください。承知の上で実行するなら --allow-ancestor-instructions を付けます（結果とレポートに記録されます）。OS の一時フォルダは Codex が拒否するので使えません。
  • 同梱スキル・組織の管理設定：Claude Code に同梱のスキルや組織の managed settings は読み込まれます。各試行で実際に読み込まれたスキル・プラグイン・MCP を記録し、レポートの「実行環境の記録」と doctor --live で確認できます。
  • ファイルアクセス：これは「どの設定を読み込むか」の隔離で、ファイルの読み書きを禁止するものではありません（Read や Bash を許可すれば絶対パスで外も読めます）。評価には合成データだけを使います。
  • 配布物の実行物：hooks・MCP サーバー・install の run は利用者の権限で動き、sandbox はありません。社内でレビュー済みの配布物だけを評価してください（validate が警告します）。

6. 採点：試行が合格・不合格・除外のどれになるか

環境のせいで落ちた試行は「失敗」に数えません。LLM 判定はコード判定が全部通ったときだけ呼ぶので（例外は図の下の ※）、結果を変えずに判定の費用を省けます。

  • ※ 配布物がないと通らない判定だけが不合格のときは、LLM 判定を省きません（ベースラインとの比較用のスコアに必要なため）。
  • スコアの分母は実際に判定したグレーダーだけです。呼ばなかった LLM 判定（skipped_prior_fail）と --no-llm のときの LLM 判定（not_run）は分母から外します。
  • UNKNOWN（判定モデルが判断できなかった）は合格にしません。実行されたグレーダーが 1 つもない試行は not_graded として除外します。
試行の状態例pass@1・pass^k の分母キャッシュ
合格全グレーダー合格入る保存
不合格形式違反・タイムアウトなど（7 章の失敗分類）入る保存（timeout は一時的な原因でも起きるので保存しない）
除外rate_limit・overloaded・auth・api_error（モデル ID の誤りなど他の API エラー）・network（Codex が再接続を繰り返しただけ）・launch_failed・harness_error・judge_error・not_graded・interrupted（Ctrl-C）入らない（件数と理由をレポートに表示）保存しない
未実行費用の上限に到達（budget_stop）入らない（件数を表示）保存しない

グレーダーの種類と書き方は リファレンス「グレーダー」 にあります。

7. 指標とリリース判定

指標定義
試行スコア合格したグレーダーの重み ÷ 判定したグレーダーの重み
試行の合格スコア 1.0 かつ失敗扱いの異常終了なし
pass@1タスクごとに「合格した有効試行 ÷ 有効試行」。全体はタスク平均
pass^kタスクごとに k 回続けて合格する確率。有効試行 n 回中 c 回合格なら C(c,k) ÷ C(n,k)。n ＝ k なら「全部合格で 1、それ以外 0」。n < k のタスクは計算せず、計算できたタスク数をレポートに出す。全体はタスク平均。同じ人が何度も使う配布物では主指標
Δ比較プロファイル − 基準プロファイル（両方に値があるタスクだけ）。配布物がないと通らない判定を両側とも除いた値で計算し、95% 区間を付ける（区間が 0 をまたげば差があるとは言えない）。あわせて pass@1 が上がった・下がったタスクの数と、正確な両側符号検定の p 値を出す（平均が上がっても一部のタスクが壊れていないかを見る。試行ではなくタスクを単位に数える）
合格あたりのコスト総コスト ÷ 合格試行数。コスト不明の試行があれば出さない（0 で埋めない）
失敗分類不合格の試行に付くタグ。異常終了の種類（timeout・max_turns・budget_exceeded・agent_error・agent_crash）と、落ちたグレーダーの category（既定値は リファレンス「グレーダー」）

pass@1 と pass^k の違い

pass@1 は「平均的にどれくらいできるか」、pass^k は「k 回続けて使っても毎回できるか」です。配布物を変えて「たまにしか失敗しなくなった」という差は、pass@1 では小さく見え、pass^k では大きく出ます。

A✓ ✓ ✓（c = 3）100%13 ÷ 3 ＝ 1
B✓ ✗ ✓（c = 2）67%01 ÷ 3 ＝ 0.33
C✗ ✗ ✓（c = 1）33%00 ÷ 3 ＝ 0
全体（タスク平均）67%0.330.44

リリース判定（gate）

前回と今回の同じプロファイルについて、タスクごとの差を作り、タスクを復元抽出するブートストラップで差の 95% 区間を出します（試行を独立な標本として数えません）。その区間を、結果を見る前に決めた「許容する悪化の幅」（マージン。--margin、毎回指定）と比べます。

判定は上の行から順に決まります。複数のプロファイルを比べるときは、1 つでも不通過なら不通過、すべて通過したときだけ通過です。

順条件判定終了コード
1定義の誤り、結果のフォルダ（summary.json・trials.jsonl）がないエラー（判定しない）2
2次のどれか
  • 安全違反の失敗分類（既定 unsafe_access。--hard-category で追加）が 1 件でもある
  • --max-regressions N（悪化してよいタスク数の上限）を付けて、前回より下がったタスクが N 件を超えた
  • 比較できない（LLM 判定の有無・タスク定義が違う、pass^k で k が違う、今回の結果にプロファイル・タスクがない、指標を算出できない）
不通過1
3比較できたタスクが --min-tasks（既定 10）未満（区間がどこにあっても）判定不能3
4区間の上端 < −マージン不通過1
5区間の下端 ≥ −マージン通過0
6それ以外（区間が −マージン をまたぐ）判定不能3

--max-regressions は、平均では通過しても一部のタスクが壊れる変更を止めるためのもので、既定では数えません。マージンと同じく結果を見る前に決めます。

タスクが少ないと区間は実際より狭く出やすいので、判断には 20 タスク以上・3 試行以上を目安にしてください（理由は 設計記録 4 章）。

8. 費用とトークン節約

キャッシュ：変えたところだけ実行する

試行の入力をすべてハッシュにしてキャッシュのキーにします。配布物を変えたプロファイルだけキーが変わるので、そのプロファイルだけが再実行されます。

キーに入るもの（1 つでも変われば再実行）キーに入れないもの（書き換えても再実行しない）
  • タスク定義・フィクスチャ・採点スクリプトの中身（グレーダーを直すと、そのタスクは全プロファイルで再実行）
  • プロファイル定義・配布物（copy 元・hash_paths）の中身
  • CLI のバージョン・試行番号・harness-eval の版（ツールを更新すると全試行を再実行）
  • 経路の変数の名前（秘密でないものは値のハッシュも。キー・トークン・ヘッダの値は使わない）
  • llm グレーダーがあるタスクだけ: --no-llm の有無・判定エージェント・モデル・判定プロンプト・判定 CLI の版・借りるプロファイルの環境変数・実行ファイル
  • タスクの説明・タグ・paired_negative・split・family
  • プロファイルの説明・billing

注意：サービス側でモデルの別名（sonnet など）が指す実体が変わっても、キーは変わりません。モデル移行の評価やリリース判定では --no-cache を付けるか、モデル ID を固定してください。

費用の上限：3 段階

  • 費用台帳 --out/spend.jsonl には、再試行・中断・doctor を含め、費用が発生するたびに 1 行追記します。--out を変えると別の台帳になります。harvest は --ledger（既定 results/spend.jsonl）に書くので、run と同じ台帳に数えるには --ledger <run の --out>/spend.jsonl を付けます。口座ごとの残りは plan で確認できます。
  • LLM 判定の費用は判定エージェントの口座に入ります。billing: subscription のプロファイルは呼び出しごとの請求がないため、月の予算には数えません（--max-cost-usd には数えます）。
  • 費用が分からない試行（pricing のない Codex、Codex での判定）は上限の計算に入りません。--jobs が 2 以上だと、実行中の分だけ上限を超えることがあります（実行前に注意を表示）。
  • 総額はエージェントと LLM 判定の合計です。どちらかが不明な試行が 1 つでもあれば「不明」と表示します。費用の出どころ（cost_source）は リファレンス「費用の出どころ」 にあります。

9. 実際の依頼からタスクを作る（harvest）

評価は、ユーザーが実際に頼む仕事で行うのがいちばん確かです。harvest は自分のセッション履歴から実際の依頼を集め、同じ種類・同じ難しさのまま、名前・数値・データをすべて架空に置き換えたタスクの下書きを作ります。元の依頼をそのまま実行したり、本物のデータや環境に触れたりはしません。

読む履歴

CLAUDE_CONFIG_DIR・CODEX_HOME を設定していればその場所を読みます。チームの履歴をまとめて使うなら --source にフォルダか履歴ファイルを並べます。

読む履歴中身取り出すもの
Claude Code history.jsonl入力欄に打った文。貼り付けは [Pasted text #1 +N lines] と pastedContents貼り付けを展開した依頼文
Claude Code projects/*/*.jsonl会話の記録。人が打った文は turnOrigin: "human"ツール結果・通知・メタ情報を除いた依頼文
Codex history.jsonl{"session_id","ts","text"}（既定で保存）text
Codex sessions/**/rollout-*.jsonlevent_msg の user_messagemessage

ツール結果・通知・/ で始まるコマンド・20 文字未満の文は除き、各セッションの最初の依頼を新しい順に --limit 件使います。

守っていること

  • 元の依頼文はメモリ上だけで扱い、ファイル・ログに書きません（表示は件数だけ）。
  • 元の名前・識別子・数値・文が残った案は 1 回作り直させ、それでも残れば見送ります。日本語の固有名詞（会社名・人名）は機械では判定できないため、人の確認が必須です。
  • LLM が書いた採点スクリプトは harvest では実行しません。人が読んだあとの validate --selftest と run で初めて実行されます。
  • 合成データだけで完結する形に書き換え、本物の環境（ssh・DB・Web）への接続を禁止し、接続を試みていないかの判定を必ず付けます。

それぞれの具体的な検査は 設計記録 6 章 にあります。

書き換えた依頼文は、元の依頼と同じく Claude（社内なら Bedrock）に送られます。

確認するときの観点：① 会社名・人名・社内システム名が残っていないか ② 依頼の性質（難しさ・曖昧さ）が元と同じか ③ 採点スクリプトが「正しいが書き方の違う答え」を落とさないか。直したら validate --selftest → run で使います。

限界：1 回の指示で完結する評価なので、確認の質問に人が答えて続く会話全体は再現できません（「確認すべき場面で確認したか」までを見ます）。各セッションの最初の依頼だけを使うため、途中で出た別の依頼は拾いません。

--keep none でも、trials.jsonl・キャッシュ・report.html には最終応答とツール呼び出しの入力（書き込んだ内容やコマンド）が残ります。評価には合成データだけを使い、結果フォルダとキャッシュを社外に出さないでください。

中断（Ctrl-C）：未開始の試行は取り消し、実行中のエージェントは子プロセスごと止めます（トークンを使い続けません）。その実行の集計とレポートは作られませんが、trials.jsonl には完了済みの試行が残ります。完了した試行はキャッシュ済みなので、同じコマンドを再実行すると続きから進みます（中断で止めた試行は interrupted としてキャッシュせず、やり直します）。

11. 自己改善ループでの使い方

配布物の変更案（候補）は外の改善役（自分で用意する claude -p のスクリプトなど。このツールには含まれません）が作り、このツールは採用してよいかを決める関門を受け持ちます。同じタスクで改善案を作って同じタスクで採点すると、そのタスクだけに効く近道も「改善」に見えるので、タスクを 3 つに分けて使います。

タスクを 3 つに分ける（split・family）

split使い道改善役に見せるか
train失敗の軌跡を読ませて改善案を作る材料見せる（結果フォルダごと）
dev候補の足切り（gate --max-regressions）合否だけ見せてよい
holdout昇格の判定（promote）だけに使う見せない（結果フォルダ・採点スクリプト・タスク定義のどれも）
  • 似たタスクは同じ family：同じ依頼から派生したタスクには同じ family を書き、同じ split に入れます（harvest の下書きは 1 件ずつ別の family なので、同じ種類の依頼から作ったものはそろえます）。1 つの family が複数の split にまたがるとき、holdout が 20 件未満のときは validate が警告します。
  • holdout は専用の --out で単独に：holdout は train・dev と同じ実行に入れられません（run・plan が止まります）。holdout 専用の --out を 1 つ決め、毎回そこへ実行します。holdout の実行はキャッシュを読まず書きません。
  • 見た回数を記録：holdout を含む実行は、開始時に <--out>/holdout_uses.jsonl に 1 行追記します（時刻・実行 ID・タスクとプロファイルの id とハッシュだけ。プロンプト・応答は書きません）。promote はここから「この holdout で評価済みの候補の数 m」を数えます。
  • 費用の台帳も別になる：費用台帳は --out ごとなので、--monthly-budget-usd は holdout 側と train・dev 側を別々に数えます。月の上限は両方の合計で考えてください。

手順

  1. タスクに split・family を書き、validate --selftest を通す。
  2. 現行の配布物で train を実行し、その実行のフォルダ（$OUT/<実行ID>）だけを改善役に渡す（run --tasks my-tasks/tasks --split train --profiles prof/current.yaml --out "$OUT"）。
  3. 改善役が候補の配布物を作る（このツールの外）。
  4. dev で足切り：gate は前回と今回の同じプロファイル id を比べるので、候補の配布物を install に書いたプロファイルを現行と同じ id（id: current）で別のフォルダに作り（下の例では prof-next/current.yaml。同じフォルダに置くと id が重複して読み込めない）、現行と候補で dev を 1 回ずつ実行して比べる。dev は 10 タスク以上（--min-tasks の既定）にする。不通過なら 3 に戻り、判定不能なら dev のタスクを増やす。
  5. holdout で昇格判定：今度は候補を別の id のプロファイル（prof/candidate.yaml、id: candidate）にし、現行と 1 回の実行で holdout を実行して promote。--candidate・--incumbent にはプロファイルの id を書きます。
  6. 昇格したら、人が変更の中身を確かめてから配布する。見送り・判定不能なら 3 に戻る。m が 10 前後になったら holdout を作り直す（偶然の勝ちが出やすくなるため）。
OUT=/Users/Shared/harness-eval; HOLDOUT=/Users/Shared/harness-eval-holdout   # holdout 専用の --out は分ける（PowerShell は README の注記どおりに読み替え）
# 4. dev で足切り（候補は現行と同じ id）
python -m harness_eval run --tasks my-tasks/tasks --split dev --profiles prof/current.yaml --out "$OUT"
python -m harness_eval run --tasks my-tasks/tasks --split dev --profiles prof-next/current.yaml --out "$OUT"
python -m harness_eval gate --current "$OUT/<候補の実行ID>" --previous "$OUT/<現行の実行ID>" --margin 0.05 --max-regressions 0
# 5. holdout で昇格判定（候補は別の id。--out は holdout 専用）
python -m harness_eval run --tasks my-tasks/tasks --split holdout --profiles prof/current.yaml prof/candidate.yaml \
    --trials 3 --out "$HOLDOUT"
python -m harness_eval promote --run "$HOLDOUT/<実行ID>" --candidate candidate --incumbent current --max-regressions 0

昇格判定（promote）の決まり方

リリース判定（gate）が「前回より悪化していないか」を見るのに対し、promote は同じ実行の中の候補と現行を比べて「良くなったと言えるか」を見ます。指標は既定で pass@1（--metric）。現行が配布物なしなら、Δ と同じく配布物がないと通らない判定を両側とも除いて比べます。判定は上の行から順に決まります。

順条件判定終了コード
1定義・オプションの値の誤り、結果のフォルダがないエラー（判定しない）2
2次のどれか
  • プロファイルが結果にない・候補と現行が同じ配布物
  • holdout 以外のタスクを含む
  • 候補に安全違反の失敗分類がある
  • 悪化したタスクが --max-regressions（必須）を超える
  • 差の推定値が 0 以下
見送り（reject）1
3次のどれか
  • 比較できたタスクが --min-tasks（既定 20）未満
  • 差の 95% 区間の下端 ≤ --min-improvement（既定 0）
  • 改善したタスクが悪化より多くない、または符号検定の p > α ÷ m（α は --alpha、既定 0.05）
  • 片側だけ値のあるタスクがある（試行がすべて除外されたなど。そこに悪化が隠れうる）
  • キャッシュの試行を含む（--any-split で holdout 以外の実行を比べたとき）
判定不能（inconclusive）3
4それ以外昇格（promote）0
  • m（評価済みの候補の数）は、台帳のうちこの holdout のタスクと 1 つでも重なる実行で評価された、現行以外の配布物の数です（同じ配布物を別の id で評価しても 1 つ。配布物なしの基準は数えない）。この実行が台帳にないときは注意を出します。
  • 符号検定はタスクを単位に数えるので、試行回数を増やしても件数は増えません。悪化 0 のとき、改善したタスクが 6 件で p = 0.031（α = 0.05・m = 1 で有意）、3 件では p = 0.25 です。試行回数は各タスクの値を安定させるために使います（3 試行以上を推奨）。
  • 参考として、現行の雑音幅（同じ配布物の試行を 2 分割した差から換算した 95% 範囲。各タスク 2 試行以上が必要）、1 試行あたりの入力側トークン（常時読み込まれる指示が増えると増える）、合格あたりコストの差も出します。判定には使いません。
  • 結果は <実行ID>/promote.json に残ります。昇格は「配布してよい」ではなく「人が確認する価値がある」という意味です。
