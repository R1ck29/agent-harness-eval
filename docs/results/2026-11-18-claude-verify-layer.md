# claude-verify-layer（検証レイヤー v0.1）の評価 E1（縮小版）

実施日: 2026-11-18 / 評価ツール: AHE 0.8.0（本体は変更していません）/ 対象: [R1ck29/agent-verify-layer](https://github.com/R1ck29/agent-verify-layer)（ブランチ `feat/v0.1`、draft PR #1。Claude 側のプラグイン名は claude-verify-layer）

**判定: 判定不能**。層なしのベースライン（P0）が、罠のタスクをすべて通した（8/8）ため、層の効果を測れませんでした。「有用」とも「有用でない」とも言えません。

## 目的とルール

新しい部品は AHE で「部品あり／なし」を比べ、有用と示せたときだけ配備する。今回の部品は、コミットの前後で `verify` スキルが行われたかを記録する層（台帳に観察を残し、`Skill(verify)` のとき、チェックリストの当たった項目を `additionalContext` として渡す。止めはしない）。結果は正直に書く。

## 方法

タスク・fixture・隠しテスト・プロファイル・実行スクリプトは、AHE ではなく **claude-verify-layer の `eval/`** にあります（[eval/README.md](https://github.com/R1ck29/agent-verify-layer/blob/feat/v0.1/eval/README.md)）。ここには書き写しません。

- **タスク 8 件**: 実際のバグ由来の罠 4 件（R1ck29 のリポジトリの fix / revert コミットから、「diff から見分けられ、コードを読むだけでは気づきにくい」不具合を選び、再び入れやすい変更依頼にした）と、チェックリストのどの項目も発火しない対照 4 件（後退の確認）。プロンプトは「変更の依頼 ＋ 最後に git にコミット」だけで、verify を使うようには頼まない
- **プロファイル 3 つ**（すべて `model: sonnet`、`billing: subscription`）:
  - P0 `claude-baseline`: 層なし。fixture のチェックリストは HEAD にあるが、何も読ませない
  - P1 `claude-static-rules`: 層なし。同じチェックリストの全項目を、常時読み込まれる CLAUDE.md に書く（「CLAUDE.md にルールを書くだけで足りるのでは」を確かめる対照）
  - P2 `claude-verify-layer`: 層あり。実際の導入と同じ経路（`scripts/install.js --apply --rules`）で hook を入れる
- **グレーダー**: 隠しテスト（主、重み 2。fixture の外にあり、コミットされた HEAD で不具合が再発していないかを決定的に判定）、コミットされているか、`git push` していないこと、参考指標（`Skill(verify)` が最後の `git commit` より前か。合否に影響しない）
- **試行**: 8 タスク × 3 プロファイル × 2 回 = 48 試行（`--jobs 2`、`--max-cost-usd 30`、`--no-cache`、`--keep all`）。モデルは claude-sonnet-5-5、Claude Code 2.1.327
- **判定基準は、結果を見る前に固定**（claude-verify-layer の `eval/RESULTS.md`）:
  - 有用 = P2 が P0 より罠のタスクで 改善 > 後退、かつ対照で後退 0
  - 判定不能 = (a) P0 の罠の合格率が 7/8 以上（天井）、(b) P2 の罠 8 回で、チェックリストの項目が 1 回も発火しない、(c) 有効な試行が 75% 未満
- AHE にタスクごとの git 準備のキーがないため、fixture を複製したあとの `install` の共通手順（`profiles/common/seed-git.sh`）で、作業ツリーを 1 コミットの git リポジトリにしました。AHE の `validate` は「ハーネスなしのベースラインがない」という警告を出しますが、これは共通の準備を `install` に持つためで、P0 は設定ディレクトリが空の、層なしのベースラインです

| 対照 合格（/8） | 8/8 | 8/8 | 8/8 |
| ターン数（中央値） | 7.5 | 9.0 | 9.0 |

- **P2 − P0**: 罠 改善 0 / 後退 1、対照 改善 0 / 後退 0。**P2 − P1**: 罠 改善 0 / 後退 1、対照 0 / 0
- P0 との差（タスクごとの平均の差の中央値）: P1 は ターン +1.5、費用 +0.0123 USD（8 タスクすべて増）。P2 は ターン +0.25、費用 +0.0025 USD（増 5・減 3）

### 台帳（観察。P2 の 16 試行のみ）

- 台帳がコミットを拾えた割合: **16/16**（verify を呼ばなかった 4 試行でも、commit 行は `none` で残った）
- 台帳の結果が実態と合う割合: **13/16**（事前の定義: 編集は Edit / Write だけを数える）。外れ 3 件のうち 2 件は、verify を編集の前に読み込み、編集のあとにテストを実行した試行で、台帳が `stale` になった**偽の stale**（この層が「verify が始まった時点のツリー」を記録する設計の限界）。1 件は、編集が Bash 経由だった試行（定義の外）
- Skill を経由せず `unittest` を直接実行した試行: 4 件（台帳は `none`。この層からは「検証していない」と「Skill を使わずに検証した」が区別できない）
- チェックリストが発火した罠の試行: 8 回のうち 4 回（`trap-fifo-bounded-read`、`trap-rejection-leak`）

## 判定と読み方

**判定不能**（事前基準の (a): P0 の罠が 8/8）。基準の表を機械的に当てはめると、罠で 改善 0 < 後退 1 なので「有用でない」側に出るが、(a) が優先する。

- 罠のタスクが、この評価では難しくなかった。P0 は何もない状態で罠 4 件を通した。P1 も 8/8
- P2 の唯一の後退は `trap-drift-scope`（2 回とも不合格）。不合格の理由は 2 回とも同じで、他者の hook が自分の hook のあとに並んでいるときに `check` が False を返した（2 回とも「自分の hook が末尾にあること」を条件に足していた）。元の不具合と同じ型の再発。ただしこの 2 回は、**どちらも verify を呼ばず、`unittest` を直接実行してコミットした**ので、層の hook は走っていない。原因は、標本のばらつき（n=2）か、P2 だけが持つ Rules の 2 行か、見分けられない
- 「P2 が P1 より良くないなら、チェックリストの注入は CLAUDE.md で代替できる」という事前の読み方は、P0・P1 とも天井だったため、示せても否定もできていない
- 層が効く機会は、Claude が verify を呼ぶかで決まる。P2 の罠 8 回のうち 4 回は呼ばなかった。fixture に verify スキルがあるため、層のない P0 でも 11/16 で呼ばれており、層が増やした行動ではない

### 限界

- n が小さい（タスク 8、1 セル 2 試行）。区間や検定は付けていない
- チェックリストの正規表現は、罠を知ったうえで書いた。実際の導入では、発火はこれより少ない
- fixture は小さな合成のライブラリで、モデルは sonnet 1 つ。P0 が天井のため、層の効果の有無は測れていない
- 台帳の「実態」の定義は、Edit / Write だけを編集と数える。Bash の heredoc などで書く試行が多く、数え方に影響する（参考値は RESULTS.md）
- E2（`/code-review` の再現率）は今回やっていない。正例が 4 件で設計の 20 件に届かない、E2 が測るのはこの層が配るものではない、実際のバグの正解キーが足りない、費用が上限を超えうる、のため

## 次にやること

- P0 の合格率が 7/8 を下回る罠（実際のコード、または fixture を大きく）を用意してから、評価を回し直す
- 層の側（仮説。この評価では確かめていない）: 罠 8 回のうち 4 回で verify が呼ばれなかったので、`git commit` の直前に、当たった項目を渡す（観察モードのまま、止めない）案を先にする。偽の stale は 2/16 で、その次
