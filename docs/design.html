1. 結論

実際の CLI（claude -p / codex exec --json）を直接呼ぶ小さな自作ツールにし、評価の統計と安全の規則をその上に載せる。依存は Python 3.10+ と PyYAML だけで、zip を展開してそのまま使える。

  • 測りたいのは「配布される形のままのハーネス（CLAUDE.md / AGENTS.md・Skills・Subagents・Hooks・MCP・モデル設定）」を載せた実際の CLI の振る舞い。SDK 経由や独自ループでは、配布設定の読み込み方が実物とずれる。
  • 社内では GitHub が使えず、インストールは Artifactory 経由の制限つき、利用者は Windows と macOS が混在、Claude は Bedrock。Docker・Node・重い Python 依存を前提にするツールは使えない。
  • 2026-10 時点で、Claude Code と Codex の両方を CLAUDE.md / AGENTS.md を含む配布物ごと、独自コードの採点と統計的なリリース判定つきで比べられる既存ツールは見つからなかった（§3）。

4. 評価の方法

指標

指標意味使いどころ
pass@1タスクごとの合格率の平均平均的にどれだけできるか
pass^kk 回続けて合格する確率（有効試行 n・合格 c なら C(c,k)/C(n,k)）毎回できるか。配布するハーネスでは主指標
比較用の値（*_cmp）配布物がないと通らない判定（スキル・サブエージェント・hook を 1 回以上使うことの要求）を除いた合否配布物なしの基準との Δ
合格あたりの費用総費用 ÷ 合格試行数。不明な費用があれば出さない品質と費用の両立

比べ方

  • 単位はタスク。同じタスクの試行は独立ではないので、試行を標本として数えない。タスクごとの値の差を作り、タスクを復元抽出するブートストラップで 95% 区間を出す（同じ seed なら同じ結果）。
  • リリース判定（gate）は前回と今回の同じプロファイルを比べる。非劣性マージン m は毎回明示する（結果を見てから決めないため、既定値を持たない）。
判定条件終了コード
通過区間の下端 ≥ −m（悪化していても m 以内と言える）0
不通過区間の上端 < −m（はっきり悪化）、安全違反の失敗分類（既定 unsafe_access）が 1 件でもある、または比べられない（k・LLM 判定の有無・タスク定義が違う）1
判定不能それ以外、または比べられたタスクが --min-tasks（既定 10）未満3

少ないタスクではパーセンタイル・ブートストラップの区間は実際より狭く出やすい（レビュー時の模擬で、12 タスク・正規分布の差のとき被覆率は 0.90 程度）。最低タスク数はそのための歯止めで、判断に使うなら 20 タスク以上を目安にする。前回より下がったタスクの一覧は判定には使わず、診断として出す。

雑音を減らす工夫

  • 同じ（試行・タスク）の各プロファイルを続けて実行し、先に走るプロファイルを試行ごとに入れ替える（--seed）。
  • レート制限・過負荷・認証・ネットワーク不通・判定を呼べないなど環境起因の終了は「除外」にし、失敗として数えない。再試行するのは環境起因だけ。
  • 各試行は空の一時ホーム・作業ディレクトリから始める（前の試行の残りが答えを漏らさない）。

採点

  • コードで決められるもの（ファイル・正規表現・独自スクリプト・ツール呼び出しの回数）を先に使う。LLM 判定は、配布物の有無に関係なく既に不合格の試行では呼ばない。観点を 1 つに絞り、根拠がなければ UNKNOWN を返させ、人手ラベル約 20 件との一致率を calibrate で確かめる。
  • 正解は元のフィクスチャから計算する（作業ディレクトリのファイルはエージェントが書き換えられる）。
  • 採点の反証: 正解例で通り、何もしなければ落ちることを validate --selftest で確かめる（同梱タスクと harvest の下書き）。

5. 費用と経路

費用の出どころ（cost_source）意味
client_estimateClaude Code が API 単価で計算した推定額（total_cost_usd）。請求額ではない
token_estimateCodex のトークン数とプロファイルの pricing から計算した概算
null（不明）取得できない。0 で埋めず、総額・合格あたり費用は「不明」
  • 月の予算（--monthly-budget-usd）は Claude と Codex で別々の口座として数える。LLM 判定の費用は判定エージェントの口座に入る。口座の記録がない旧形式の台帳の行は、どちらにも数える（安全側）。
  • billing: subscription のプロファイルは呼び出しごとの請求がないため、推定額は台帳に残すが月の予算には数えない。--max-cost-usd（1 回の実行の大きさの上限）には数える。
  • 経路・請求先・モデルの実体を変える環境変数（各 CLI の実行ファイルに名前があることを確認したもの）を親から黙って引き継ぐと、意図しない口座で動き、キャッシュにも反映されない。値を固定するものは env、親の値を使うもの（秘密）は inherit_env に名前だけ書く。宣言のない引き継ぎは doctor が NG、run が警告（LLM 判定の経路も含む）。
  • キャッシュキーには経路の変数の名前が入る。秘密でないもの（モデルの別名の実体・接続先・切り替え）は値の短いハッシュも入れ、値を変えれば再実行される。キー・トークン・ヘッダの値は使わない。

6. 信頼の境界

  • 隔離は「どの設定を読み込むか」の隔離で、ファイルアクセスやネットワークの制限ではない。評価には合成データだけを使う。
  • 配布物の hooks・MCP サーバー・install の run は利用者の権限で動く。sandbox がないため、未レビューの実行物を安全に評価する手段はない（Phase 0 の T2/T3 に当たるものは扱わない）。社内でレビュー済みの配布物だけを評価し、validate の警告で実行される部品に気づけるようにしている。
  • harvest は LLM が書いた採点スクリプトを実行しない（人が読んだ後の validate --selftest で実行）。元の依頼文はメモリ上だけで扱う。

7. 採らなかった案

案理由
BenchFlow / Inspect / Harbor を実行エンジンにするDocker と重い依存が必要で、社内の配布・インストールの制約に合わない
Promptfoo を実行エンジンにするNode が必要。SDK 経由で CLI 本体と同一とは限らず、配布設定の読み込みを測る目的とずれる
claude plugin eval だけで済ませるCodex 非対応、CLAUDE.md・ユーザー設定を読まない、独自コードで採点できない（スキル単体の確認には併用できる）
リリース判定の既定マージン結果を見てからの調整を防ぐため、毎回明示させる
Decimal による予算計算セント単位の上限には float で十分で、概念を 1 つ減らせる
Codex の --ignore-user-config$CODEX_HOME/config.toml を読まなくなり、配布物の hooks・MCP 設定まで無効になる（0.146.1 のヘルプで確認）。CODEX_HOME は既に一時ホーム
CLI の --help でフラグの有無を調べる診断Claude Code は --max-turns をヘルプに出さないため誤って NG になる。実際に動くかは doctor --live で確かめる
早期打ち切り（不合格が出たら残り試行をやめる）pass@1 と平均スコアが不合格側に偏る
LLM 判定の --system-prompt 差し替え・--json-schema実測で入力トークンが減らない／費用が同程度で、今の解析に失敗がない
試行の --exclude-dynamic-system-prompt-sections・--bare節約の余地が小さい一方、プロンプトの形や CLAUDE.md・ログインの読み込みが変わり、配布物どおりの評価にならない
生成された採点スクリプトを静的検査して自動実行Python の安全性は静的に確かめきれない（許可した標準モジュールだけでもコマンド実行や通信ができる書き方が見つかった）
提供元ゲートウェイでの強制停止・封印した holdout・egress の強制と持ち出し攻撃のテスト（Phase 0 の未着手項目）社内ゲートウェイ・別の認証情報・sandbox が必要で、この配布形態では実現できない。台帳による上限、架空化したタスク、レビュー済みの配布物だけを評価する運用で代える
plugin eval のケース形式との相互変換今は必要としている利用者がいない

8. 残るリスク・未確認

  • Windows の実機、Codex での実際のエージェント実行、macOS キーチェーンのログインを一時ホームで使えるかは未確認。社内では最初に doctor・doctor --live・harvest --dry-run を通す。
  • 統合を行った開発機の CLI（Claude Code 2.1.295・Codex 0.146.1）は、起動フラグと出力形式を確かめた版（2.1.304・0.163.0）より古い。使うフラグはどちらのヘルプにもある（Claude の --max-turns は非表示の既存フラグ）が、出力形式の違いは doctor --live で確かめる。
  • Claude Code の同梱スキル・組織の管理設定は一時ホームでも読み込まれる。試行ごとに実際に読み込まれた構成要素を記録し、レポートで見えるようにしている。
  • 少ないタスクでは区間が狭く出やすい（§4）。判断には 20 タスク以上・3 試行以上を目安にする。
  • harvest の架空化は日本語の固有名詞を機械で判定できない。下書きは人が確認してから使う。
  • doctor は LLM 判定の経路を見ない（判定の有無は実行時の指定で決まるため）。判定が親の環境で動くときの経路の警告は run が出す。
