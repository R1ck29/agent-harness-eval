1. 結論

実際の CLI（claude -p / codex exec --json）を直接呼ぶ小さな自作ツールにし、評価の統計と安全の規則をその上に載せる。依存は Python 3.10+ と PyYAML だけで、zip を展開してそのまま使える。

  • 測りたいのは「配布される形のままのハーネス（CLAUDE.md / AGENTS.md・Skills・Subagents・Hooks・MCP・モデル設定）」を載せた実際の CLI の振る舞い。SDK 経由や独自ループでは、配布設定の読み込み方が実物とずれる。
  • 社内では GitHub が使えず、インストールは Artifactory 経由の制限つき、利用者は Windows と macOS が混在、Claude は Bedrock。Docker・Node・重い Python 依存を前提にするツールは使えない。
  • 2026-10 時点で、Claude Code と Codex の両方を CLAUDE.md / AGENTS.md を含む配布物ごと、独自コードの採点と統計的なリリース判定つきで比べられる既存ツールは見つからなかった（§3）。

4. 評価の方法

指標

pass@1・pass^k・Δ の定義と計算例は 図解ガイド 7 章 にあります。配布するハーネスは同じ人が何度も使うので、毎回できるかを見る pass^k を主指標にする。Δ の扱いの理由は §2 の 2。

比べ方

  • 単位はタスク。同じタスクの試行は独立ではないので、試行を標本として数えない。タスクごとの値の差を作り、タスクを復元抽出するブートストラップで 95% 区間を出す（乱数の種は固定なので、同じ結果からは何度計算しても同じ区間になる。--seed は実行順だけに効く）。
  • リリース判定（gate）は前回と今回の同じプロファイルを比べる。非劣性マージン（許容する悪化の幅）は毎回明示する（結果を見てから決めないため、既定値を持たない）。
  • 変更案の採否（promote）は、同じ実行の中の候補と現行を比べる優越性の判定で、リリース判定とは分ける（§10）。

判定（通過・不通過・判定不能）の条件と終了コードは 図解ガイド 7 章 にあります。

少ないタスクではパーセンタイル・ブートストラップの区間は実際より狭く出やすい（レビュー時の模擬で、12 タスク・正規分布の差のとき被覆率は 0.90 程度）。最低タスク数はそのための歯止めで、判断に使うなら 20 タスク以上を目安にする。前回より下がったタスクの一覧は判定には使わず、診断として出す。

雑音を減らす工夫

  • プロファイルを交互に並べて実行する（§2 の 3。並べ方の図は 図解ガイド 3 章）。
  • レート制限・過負荷・認証・ネットワーク不通・判定を呼べないなど環境起因の終了は「除外」にし、失敗として数えない。再試行するのは環境起因だけ。
  • 各試行は空の一時ホーム・作業ディレクトリから始める（前の試行の残りが答えを漏らさない）。

採点

  • コードで決められるもの（ファイル・正規表現・独自スクリプト・ツール呼び出しの回数）を先に使う。LLM 判定は補助にとどめ、合否が変わらない試行では呼ばない（規則は 図解ガイド 6 章）。観点を 1 つに絞り、根拠がなければ UNKNOWN を返させ、人手ラベル約 20 件との一致率を calibrate で確かめる。
  • 正解は元のフィクスチャから計算する（作業ディレクトリのファイルはエージェントが書き換えられる）。
  • 採点の反証: 正解例で通り、何もしなければ落ちることを validate --selftest で確かめる（同梱タスクと harvest の下書き）。

5. 費用と経路

仕組みは 図解ガイド 8 章、書き方は リファレンス 5 章・8 章 にあります。ここでは判断の理由だけを記録します。

判断理由
費用の出どころ（cost_source）を区別し、不明を 0 で埋めないCLI の推定額を「報告値」と呼ぶと請求額と誤解される。0 で埋めると合格あたり費用が実際より安く見える
月の予算は Claude と Codex を別々の口座として数える。口座の記録がない旧形式の台帳の行は、どちらにも数える旧評価基盤で決めた予算の方針（別々の月額上限）。旧形式の扱いは安全側に倒した
billing: subscription は月の予算に数えないが、--max-cost-usd には数える定額契約に架空の請求額を付けない。一方で 1 回の実行の大きさの歯止めは必要
経路を変える環境変数は、env か inherit_env（名前だけ）で宣言させる。宣言のない引き継ぎと、宣言したのに未設定の変数は doctor が NG試行は親の環境を引き継ぐため、残っていた API キーなどで経路・口座・モデルが黙って変わる。値をプロファイルに書かせると秘密が漏れる（レビューで指摘を受けて名前だけに変更）。未設定の検知は、別の端末で export して全試行が未ログインになった実測から
経路の変数をキャッシュのキーに入れる。秘密でないものは値の短いハッシュも入れ、キー・トークン・ヘッダの値は使わない経路を変えたのに過去の結果を再利用しないため。秘密の値はハッシュでもファイルに残さない

6. 信頼の境界

判断：sandbox は持たない。隔離は「どの設定を読み込むか」に限り、評価の対象を「社内でレビュー済みの配布物」と「合成データ」に絞る運用で安全を保つ。

  • 理由: Docker などの sandbox は社内の配布・インストールの制約で使えない（§1）。sandbox がなければ、未レビューの実行物（旧評価基盤の T2/T3 に当たるもの）を安全に評価する手段はないので、扱わないと決めて validate の警告で気づけるようにした。
  • harvest が LLM の書いた採点スクリプトを実行しないのも同じ理由（§7「生成された採点スクリプトを静的検査して自動実行」）。
  • 何が隔離され、何が隔離されないかは 図解ガイド 5 章 にあります。

harvest の安全策

心配対策
依頼文の社外秘が残る書き換えの指示で、固有名詞・数値・日付・表名などを架空にする。元の依頼にある識別子（db.table・snake_case・ファイル名）・URL・メール・大文字の名前（NOVA など）・年月・4 桁以上の数値（4 桁は合成データの値との偶然の一致を除く）や、25 文字以上の同じ文が残った案は、残った値を具体的に伝えて 1 回作り直させ、それでも残れば見送る（全角半角・大文字小文字・改行・年月の書き方の違いは無視して比べる）。日本語の固有名詞は機械で判定できない（§11）
依頼文がファイルやログに残る元の依頼文はメモリ上だけで扱い、表示は件数だけ。書き換えの呼び出しでも新しい履歴を作らない。テレメトリのプロンプト記録（OTEL_LOG_USER_PROMPTS・OTEL_LOG_TOOL_DETAILS）の環境変数は外して呼ぶ（組織の管理設定で有効にされている場合は外せない）
LLM が書いた採点スクリプトharvest では実行しない（構文の確認だけ）。実行するのは、人が中身を読んだあとの validate --selftest と run
設定ファイルを紛れ込ませる合成データの置き場所に、. で始まるもの（.claude/・.mcp.json）と指示ファイル（CLAUDE.md・AGENTS.md など。一覧は 図解ガイド 5 章）は置かせない
本物の環境で実行してしまう合成データだけで完結する形に書き換える。Claude Code では ssh・scp・sftp・curl・wget・trino・hive・beeline・psql・mysql・WebFetch・WebSearch を禁止する。ただし Bash 自体は許可するので、Python からの通信などまでは防げない（最善の努力）。Codex にはこの禁止が効かないので、codex_sandbox: workspace-write（既定でネットワーク不可）で制限する。Bedrock 認証のため本物の AWS 認証ファイルは参照できる状態なので、合成データ以外を置かない
接続を試みても気づけない生成したタスクには「本物の環境（ssh・DB・Web）に接続しようとしていない」という過程の判定を必ず付ける（禁止で止められた呼び出しも記録に残るので、試みも数える）
採点が不公平正解例で通り、何もしなければ落ちることを自動で確かめる。依頼で求めていない判定（例: 最終応答に特定の店名）は外す
未ログインのまま全件失敗認証エラーなら最初の 1 件で止める（--profile で認証を借りるプロファイルを指定できる）

7. 採らなかった案

案理由
BenchFlow / Inspect / Harbor を実行エンジンにするDocker と重い依存が必要で、社内の配布・インストールの制約に合わない
Promptfoo を実行エンジンにするNode が必要。SDK 経由で CLI 本体と同一とは限らず、配布設定の読み込みを測る目的とずれる
claude plugin eval だけで済ませるCodex 非対応、CLAUDE.md・ユーザー設定を読まない、独自コードで採点できない（スキル単体の確認には併用できる）
リリース判定の既定マージン結果を見てからの調整を防ぐため、毎回明示させる
Decimal による予算計算セント単位の上限には float で十分で、概念を 1 つ減らせる
Codex の --ignore-user-config$CODEX_HOME/config.toml を読まなくなり、配布物の hooks・MCP 設定まで無効になる（0.146.1 のヘルプで確認）。CODEX_HOME は既に一時ホーム
CLI の --help でフラグの有無を調べる診断Claude Code は --max-turns をヘルプに出さないため誤って NG になる。実際に動くかは doctor --live で確かめる
早期打ち切り（不合格が出たら残り試行をやめる）pass@1 と平均スコアが不合格側に偏る
LLM 判定の --system-prompt 差し替え・--json-schema実測で入力トークンが減らない／費用が同程度で、今の解析に失敗がない
試行の --exclude-dynamic-system-prompt-sections・--bare節約の余地が小さい一方、プロンプトの形や CLAUDE.md・ログインの読み込みが変わり、配布物どおりの評価にならない
生成された採点スクリプトを静的検査して自動実行Python の安全性は静的に確かめきれない（許可した標準モジュールだけでもコマンド実行や通信ができる書き方が見つかった）
提供元ゲートウェイでの強制停止・別の認証情報で封印した holdout・egress の強制と持ち出し攻撃のテスト（旧評価基盤 の未着手項目）社内ゲートウェイ・別の認証情報・sandbox が必要で、この配布形態では実現できない。台帳による上限、架空化したタスク、レビュー済みの配布物だけを評価する運用で代える。holdout の封印は、フォルダの分離（holdout 専用の --out に単独で実行し、他の分割と混ぜると止める）と holdout 利用台帳（見た回数を数える）で代える（v0.5.0）
promote に「同じ回数の best-of-N」の対照を入れる（v0.5.0 で検討）配布物の変更は利用時に 1 依頼 1 回の実行なので、利用時の計算量は候補と現行で同じ。best-of-N は 1 依頼に複数回の実行を使う手法（Harness² のタスクごとの適応や、arXiv:2607.12227 が比べた試験時の手法）を比べるための対照。候補を多数試したことによる偶然の勝ちは、改善に使わない holdout と α / m の補正で扱う。配布物そのものが複数回の実行を使う場合（自己一貫性のスキルなど）は、合格あたりコストで比べる
改善役にファイルを直接書かせる（Write・Edit を許す）（v0.6.0 で検討）書き込みを許すと、作業フォルダの外や採点に関わるファイルへの書き込みを権限設定だけで防ぐことになる。読み取りだけにして変更項目を構造化出力で返させれば、当てる・検査するのはツール側で、項目ごとに記録も残る
改善役に Bash を許す権限設定の Read の deny は Read・Grep・Glob にしか効かず、cat で迂回できる
作業フォルダの外を読めない既定の動作だけに頼る権限モードを指定しないと 2.1.295 の -p は auto で始まり（§8）、組織の管理設定で読める場所が足されることもある。作業フォルダの制限と deny の 2 段にし、起動ごとに deny が効くかを確かめる
自己確認に通らないときも、指定すれば改善役を起動できるようにする確かめられないまま holdout を読める状態で起動すると、v0.5.0 の分離が意味を失う（利用者の指示: 確かめられなければ止める）
各利用者の設定（~/.claude/CLAUDE.md など）を利用者ごとに自動で最適化する（2026-10-31 に利用者と決定）1 人分のタスクでは holdout を作れず検証できない、端末ごとに評価の費用がかかる、配布物が人ごとに分かれて比べられなくなる。改善は全員に配る配布物に中央でかけ、個人の設定は将来「提案して本人が確認」の形にする（自動では書き換えない）
昇格した候補を人の確認なしに全員へ配る正解のない自己評価で採否を決めると held-out で改善が消える・評価を改竄する例がある（arXiv:2607.12227、Darwin Gödel Machine）。Windows は開発機で試験できない。昇格は「人が確認する価値がある」の意味にし、配布は承認のあと段階的に行う
plugin eval のケース形式との相互変換今は必要としている利用者がいない

8. 実機・ソースで確かめた CLI の挙動

doctor は、ここで確かめた版（Claude Code 2.1.304・Codex 0.163.0）より古い CLI を知らせます。

10. 自己改善ループとの関係（v0.5.0・v0.6.0）

このツールは自己改善ループの「採否を決める関門」を受け持ち、v0.6.0 からは変更案を作る改善役（improve）も持つ。配布先の利用者全体から学んで配布ハーネスが良くなる形を目標にし、v0.5.0 で評価側の土台を、v0.6.0 で改善役を作った。

  • 計算量をそろえた再評価では、自動のハーネス改善は held-out で平均 +0.0、改善は「タスク固有の近道」だった（arXiv:2607.12227。再評価したのは AHE のみ）。
  • 改善を報告した研究で効いていたのは関門だった。回帰予算を外すと GRASP は 88.8 → 81.8、開発セットの関門を外すと AutoSaddler は GAIA2 で 62.0 → 50.6。
  • 評価が改善役から見えると、評価そのものを改竄する（Darwin Gödel Machine）。Meta-Harness は改善役に test の結果を見せない。

使い方と判定の決まり方は 図解ガイド 11 章 にあります。

v0.5.0 で加えたもの

#加えたもの出どころ理由
1タスクの split（train / dev / holdout）と family。run --split。1 つの family が複数の分割にまたがると警告AutoSaddler・arXiv:2607.12227（グループ単位の分割）、Meta-Harness同じ依頼から派生した似たタスクが分割をまたぐと答えが漏れる
2holdout と他のタスクを 1 回の実行に混ぜると止める。holdout の実行はキャッシュを読まず書かないMeta-Harness、Darwin Gödel Machine改善役に渡す結果フォルダ・共有のキャッシュに holdout のトランスクリプトを入れない。候補と現行を同じ時点で実行する
3holdout 利用台帳（holdout_uses.jsonl。id とハッシュだけ）holdout の使い回しによる過学習、社内の「プロンプトをログに書かない」規則holdout を見るたびに偶然の勝ちが出やすくなる。回数を多重比較の補正に使う
4タスク単位の改善・悪化の数と正確な両側符号検定（Δ・gate・promote）The Regression Tax（arXiv:2607.22520。回帰が改善の 59% を打ち消した。正確 McNemar）区間だけでは、平均が上がって一部のタスクが壊れる変更が見えない
5gate --max-regressions（回帰予算）GRASP（arXiv:2605.29668）の R(c) ≤ R₀リリース判定でも、宣言した件数を超える悪化を止められる（既定は数えず v0.4.0 と同じ）
6promote（同じ実行の中で候補と現行を比べる優越性の 3 値判定。回帰予算は必須、有意水準は α ÷ 評価済みの候補の数。評価済みの候補はタスクの重なりで数える）GRASP、AutoSaddler、Bonferroni 補正リリースゲート（非劣性）とは別に、「採用してよいか」を決める。符号検定は両側なので、悪化の多い候補が有意にならないよう改善が悪化より多いことも求める。片側だけ値のあるタスクがあれば昇格にしない（環境起因の除外はプロファイルごとに偏ることがあり、そこに悪化が隠れる）。holdout を 1 件足し引きしても補正が 1 に戻らないよう、評価済みの候補は完全一致ではなく重なりで数える
7現行の雑音幅（同じ配布物の試行を 2 分割した差の 95% 範囲。参考表示）A/A テスト同じ配布物どうしでどの程度の差が出るかを並べて見る

v0.6.0 で加えたもの（改善役）

v0.5.0 では、研究で効いていたのが改善案の作り方より関門だったことから、先に関門を固めて改善役は外に置いた（2026-10-29）。関門ができたので、利用者の依頼（2026-10-31）で改善役を入れた。改善役で一番危ないのは holdout を見てしまうこと（見れば holdout は改善に使ったデータになり、昇格判定が意味を失う）なので、読み取りの制限を中心に作った。

#加えたもの出どころ理由
1読み取りだけの改善役。材料（train の失敗した試行と現行の配布物）は一時フォルダに写して渡し、元の実行フォルダ・タスク定義・holdout の --out は権限設定の deny で読ませないMeta-Harness（改善役に test を見せない）、Darwin Gödel Machine（評価が見えると改竄する）写しにすれば元の場所をまるごと deny でき、何を見せたかもはっきりする
2起動ごとの自己確認（偽の API で deny が効くかを確かめ、確かめられなければ止める）§8 の実機確認、利用者の指示deny の効き方は CLI の版・OS・パスの書き方で変わりうる（[ ] と \ は実際に違った）。社内の Windows や将来の版でも、動かすその場で確かめる
3変更項目を作業手順（INV）と業務知識（DOM）に分け、項目ごとに追記・置き換え・削除で返させるHarness²（INV / DOM）、ACE（項目ごとの差分）まとめて書き直させると、どの変更が効いたか・壊したかが分からず、良い部分まで失われやすい
4直ると予想するタスクを書かせ、次の回で当たったかを照合して改善役にも見せるHarness²当たらない予想が続くなら、改善役が失敗の原因を読み違えている
5評価の前の事前検査（train 固有の文字列・採点に関わる変更・常時読み込まれる指示の増加）arXiv:2607.12227（改善は「タスク固有の近道」だった）、The Regression Tax（指示を足すほど他が壊れる）明らかな近道と肥大化は、費用のかかる評価の前に落とす。言い換えた近道は見つけられないので、採否は holdout で決める
6スキルの候補を「なし／説明文だけ／説明文＋本文」の 3 つのプロファイルで比べる（skill-variants でも作れる）The Regression Tax（説明文だけでも振る舞いが変わる）説明文の効果（呼ばれ方の変化）と本文の効果を分けて見る

改善の対象は 2 層に分けて考える（利用者と決定、2026-10-31）。共有の層は全員に配る配布物で、改善役が複数の利用者から集めた材料をもとに中央で改善し、複数の利用者の架空化したタスクで作った holdout の promote を通ったときだけ配る（1 人にしか効かない変更は配らない）。個人の層は各利用者の ~/.claude/CLAUDE.md などで、v0.6.0 では扱わない（将来は提案して本人が確認する形にし、自動では書き換えない。理由は §7）。

配布先全体での自己改善（目標の構成）

層何をするか状態
① 利用者の端末（収集）配布ハーネスの hooks と OTEL で、内容を含まない信号を集める（スキル・ツールの失敗、再試行、やり直し、費用、中断など）。プロンプト本文は送らない。実際の依頼の「型」は、各端末で harvest を実行し、架空化したタスクだけを送る案がある未実装。方針（利用者、2026-10-31）: 内容を含まない信号と架空化したタスクは、許される範囲でできる限り集める。社内で何が許可されているかは未確認なので、収集は信号の種類ごとに有効・無効を切り替えられる形にし、許可が分かった時点で絞る
② 中央（配布担当の環境）信号から弱い所を特定 → 改善役（claude -p）が train の失敗を読んで候補を作る → このツールで dev（gate --max-regressions）→ holdout（promote）関門（split・台帳・符号検定・回帰予算・promote）は v0.5.0、改善役（improve）は v0.6.0 で実装。弱い所の特定（信号の集計）は未実装
③ 配布昇格した候補を人が確認・承認 → プラグインの新しい版を本人 → エンジニアのパイロット → Windows のコンサルタント → 全員の順に展開。OTEL の指標を前の版と比べ、悪化したら前の版に戻す未実装（配布の仕組みは既存のプラグイン配布を使う）

自動にする範囲: 信号の集計、候補の作成、評価、昇格判定、段階配布、悪化時の前の版への切り戻し。人が入るのは全員への配布の前の承認 1 回（推奨。利用者の判断待ち）。

残タスク（次の版の候補）

  • OTEL の信号を中央で集計し、弱い所（失敗の多いスキル・ツール）を改善の対象として出す部分。利用者から信号を戻す経路は別に調べている（Windows・Mac の Outlook を含む）ので、v0.6.0 では作らない。
  • 段階配布中の自動比較と切り戻し（OTEL の指標で前の版と比べる）。
  • 個人の層の「提案して本人が確認」の仕組み（上の 2 層）。

11. 残るリスク・未確認

  • Windows は未検証（テストは Linux と macOS、Python 3.10〜3.13）。パスは pathlib、タイムアウト時の停止は taskkill /T を使う実装。CLI が npm の claude.cmd だと --settings の JSON などが cmd.exe を経由するので、問題が出たら executable: で実体（.exe や node + スクリプト）を指定する。社内の Windows 端末で doctor --live とスモーク評価を一度通してから展開する。
  • Codex での実際のエージェント実行は未確認（開発環境から OpenAI API に接続できない）。パーサは実出力（失敗時）とソースのイベント定義から作ったテストデータで検証している。社内では最初に doctor --live を通す。
  • 開発機の CLI（Claude Code 2.1.295・Codex 0.146.1）は §8 で確かめた版より古い。使うフラグはどちらのヘルプにもある（Claude の --max-turns は非表示の既存フラグ）が、出力形式の違いは doctor --live で確かめる。
  • 上のフォルダの指示・同梱スキル・組織の管理設定は一時ホームでは隔離できない（図解ガイド 5 章）。
  • harvest の架空化は日本語の固有名詞を機械で判定できない。下書きは人が確認してから使う。
  • doctor は LLM 判定の経路を見ない（判定の有無は実行時の指定で決まるため）。判定が親の環境で動くときの経路の警告は run が出す。
  • MCP のモックサーバーは同梱していない（install で設定ファイルを置き、extra_args で --mcp-config を渡す）。
  • holdout を読ませない仕組みは改善役（improve）だけのもの。run・promote を操作する人や、自分で用意した別の改善役からは holdout が見える。holdout は別の端末・別のユーザーに置けるならそうする。
  • 改善役の読み取りの制限は、本物のモデルでの実行をまだ確かめていない（開発機の CLI にログインがなく、手元の偽の API で CLI の権限の判定を確かめた。§8）。社内で最初の improve を動かしたら、improve.json の permission_denials と isolation_check を確かめる。
  • Windows での deny の書き方（//C:/… と //c/… の両方を書く）は未確認。効かなければ自己確認が漏れを見つけて improve が止まる（安全側だが、そのままでは改善役を使えない）。組織の管理設定が接続先や権限モードを固定していると、自己確認が偽の API につながらず同じく止まる。
  • POSIX で、読ませない場所のパスに \ を含むと deny で止められない（§8）ので、improve は起動しない。フォルダ名を変える。
  • 事前検査は文字列の照合なので、言い換えた近道や句読点を挟んだ写しは通る。一方で、train の依頼文にある一般的な語（4 桁以上の数値・大文字の名前など）を新しく書いた項目は、近道でなくても見送られることがある。見送りは理由（項目 id）を見てもう一度実行する。採否は holdout で決める。
  • promote の多重比較の補正は、同じ台帳（既定は結果フォルダの親の holdout_uses.jsonl）に記録された分しか数えない。別の --out で同じ holdout を試した分は数えないので、holdout は 1 つの --out で使う。
  • v0.4.0 以前の結果を promote --any-split で比べると、現行が配布物なしかどうかが記録にないため、配布物がないと通らない判定を除かずに比べる（候補に有利に出る）。試験用の使い方で、昇格の根拠にはしない。
  • 実際の CLI での holdout 実行・promote は未実施（偽 CLI の e2e テストだけ）。最初の候補で doctor --live → holdout の実行 → promote を一度通してから使う。
