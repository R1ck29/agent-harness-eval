1. 結論

実際の CLI（claude -p / codex exec --json）を直接呼ぶ小さな自作ツールにし、評価の統計と安全の規則をその上に載せる。依存は Python 3.10+ と PyYAML だけで、zip を展開してそのまま使える。

  • 測りたいのは「配布される形のままのハーネス（CLAUDE.md / AGENTS.md・Skills・Subagents・Hooks・MCP・モデル設定）」を載せた実際の CLI の振る舞い。SDK 経由や独自ループでは、配布設定の読み込み方が実物とずれる。
  • 社内では GitHub が使えず、インストールは Artifactory 経由の制限つき、利用者は Windows と macOS が混在、Claude は Bedrock。Docker・Node・重い Python 依存を前提にするツールは使えない。
  • 2026-10 時点で、Claude Code と Codex の両方を CLAUDE.md / AGENTS.md を含む配布物ごと、独自コードの採点と統計的なリリース判定つきで比べられる既存ツールは見つからなかった（§3）。

4. 評価の方法

指標

pass@1・pass^k・Δ の定義と計算例は 図解ガイド 7 章 にあります。配布するハーネスは同じ人が何度も使うので、毎回できるかを見る pass^k を主指標にする。Δ の扱いの理由は §2 の 2。

比べ方

  • 単位はタスク。同じタスクの試行は独立ではないので、試行を標本として数えない。タスクごとの値の差を作り、タスクを復元抽出するブートストラップで 95% 区間を出す（乱数の種は固定なので、同じ結果からは何度計算しても同じ区間になる。--seed は実行順だけに効く）。
  • リリース判定（gate）は前回と今回の同じプロファイルを比べる。非劣性マージン m は毎回明示する（結果を見てから決めないため、既定値を持たない）。

判定（通過・不通過・判定不能）の条件と終了コードは 図解ガイド 7 章 にあります。

少ないタスクではパーセンタイル・ブートストラップの区間は実際より狭く出やすい（レビュー時の模擬で、12 タスク・正規分布の差のとき被覆率は 0.90 程度）。最低タスク数はそのための歯止めで、判断に使うなら 20 タスク以上を目安にする。前回より下がったタスクの一覧は判定には使わず、診断として出す。

雑音を減らす工夫

  • プロファイルを交互に並べて実行する（§2 の 3。並べ方の図は 図解ガイド 3 章）。
  • レート制限・過負荷・認証・ネットワーク不通・判定を呼べないなど環境起因の終了は「除外」にし、失敗として数えない。再試行するのは環境起因だけ。
  • 各試行は空の一時ホーム・作業ディレクトリから始める（前の試行の残りが答えを漏らさない）。

採点

  • コードで決められるもの（ファイル・正規表現・独自スクリプト・ツール呼び出しの回数）を先に使う。LLM 判定は補助にとどめ、合否が変わらない試行では呼ばない（規則は 図解ガイド 6 章）。観点を 1 つに絞り、根拠がなければ UNKNOWN を返させ、人手ラベル約 20 件との一致率を calibrate で確かめる。
  • 正解は元のフィクスチャから計算する（作業ディレクトリのファイルはエージェントが書き換えられる）。
  • 採点の反証: 正解例で通り、何もしなければ落ちることを validate --selftest で確かめる（同梱タスクと harvest の下書き）。

5. 費用と経路

仕組みは 図解ガイド 8 章、書き方は リファレンス 5 章・8 章 にあります。ここでは判断の理由だけを記録します。

判断理由
費用の出どころ（cost_source）を区別し、不明を 0 で埋めないCLI の推定額を「報告値」と呼ぶと請求額と誤解される。0 で埋めると合格あたり費用が実際より安く見える
月の予算は Claude と Codex を別々の口座として数える。口座の記録がない旧形式の台帳の行は、どちらにも数える旧評価基盤で決めた予算の方針（別々の月額上限）。旧形式の扱いは安全側に倒した
billing: subscription は月の予算に数えないが、--max-cost-usd には数える定額契約に架空の請求額を付けない。一方で 1 回の実行の大きさの歯止めは必要
経路を変える環境変数は、env か inherit_env（名前だけ）で宣言させる。宣言のない引き継ぎと、宣言したのに未設定の変数は doctor が NG試行は親の環境を引き継ぐため、残っていた API キーなどで経路・口座・モデルが黙って変わる。値をプロファイルに書かせると秘密が漏れる（レビューで指摘を受けて名前だけに変更）。未設定の検知は、別の端末で export して全試行が未ログインになった実測から
経路の変数をキャッシュのキーに入れる。秘密でないものは値の短いハッシュも入れ、キー・トークン・ヘッダの値は使わない経路を変えたのに過去の結果を再利用しないため。秘密の値はハッシュでもファイルに残さない

6. 信頼の境界

判断：sandbox は持たない。隔離は「どの設定を読み込むか」に限り、評価の対象を「社内でレビュー済みの配布物」と「合成データ」に絞る運用で安全を保つ。

  • 理由: Docker などの sandbox は社内の配布・インストールの制約で使えない（§1）。sandbox がなければ、未レビューの実行物（旧評価基盤の T2/T3 に当たるもの）を安全に評価する手段はないので、扱わないと決めて validate の警告で気づけるようにした。
  • harvest が LLM の書いた採点スクリプトを実行しないのも同じ理由（§7「生成された採点スクリプトを静的検査して自動実行」）。
  • 何が隔離され、何が隔離されないかは 図解ガイド 5 章 にあります。

10. 残るリスク・未確認

  • Windows は未検証（テストは Linux と macOS、Python 3.10〜3.13）。パスは pathlib、タイムアウト時の停止は taskkill /T を使う実装。CLI が npm の claude.cmd だと --settings の JSON などが cmd.exe を経由するので、問題が出たら executable: で実体（.exe や node + スクリプト）を指定する。社内の Windows 端末で doctor --live とスモーク評価を一度通してから展開する。
  • Codex での実際のエージェント実行は未確認（開発環境から OpenAI API に接続できない）。パーサは実出力（失敗時）とソースのイベント定義から作ったテストデータで検証している。社内では最初に doctor --live を通す。
  • 開発機の CLI（Claude Code 2.1.295・Codex 0.146.1）は §8 で確かめた版より古い。使うフラグはどちらのヘルプにもある（Claude の --max-turns は非表示の既存フラグ）が、出力形式の違いは doctor --live で確かめる。
  • 上のフォルダの指示・同梱スキル・組織の管理設定は一時ホームでは隔離できない（図解ガイド 5 章）。
  • harvest の架空化は日本語の固有名詞を機械で判定できない。下書きは人が確認してから使う。
  • doctor は LLM 判定の経路を見ない（判定の有無は実行時の指定で決まるため）。判定が親の環境で動くときの経路の警告は run が出す。
  • MCP のモックサーバーは同梱していない（install で設定ファイルを置き、extra_args で --mcp-config を渡す）。

  • Anthropic: Demystifying evals for AI agents（タスク・試行・採点、pass@k と pass^k、判定の較正、試行ごとのクリーンな環境）

  • Anthropic: Quantifying infrastructure noise in agentic coding evals（資源設定だけで 6 ポイント動く、3 ポイント未満の差に注意）
